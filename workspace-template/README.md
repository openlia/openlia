# Personal OS Workspace

This directory is a small, file-based model of a personal operating system. It
is copied into an empty runtime workspace; later profile syncs seed missing
starter files without replacing existing workspace files.

`workspace.yaml` is the user-owned registry for this workspace. It records the
core domains seeded by OpenLia and any approved nested or top-level extensions.
Hermes must read it before proposing a destination. The registry is descriptive:
it does not create directories or authorize writes by itself.

`assistant-policy.yaml` is the user-owned authority policy. The starter policy
enables routine local workspace management automatically, including clear
capture, filing, record updates, reports, and local Git history. It does not
authorize external side effects or destructive operations. Edit the policy to
narrow or expand delegation; existing user edits survive profile sync.

## Canonical directories

- `inbox/`: uncategorized captures waiting for review.
- `goals/`: outcomes and the reason they matter (`goal-template.md`).
- `areas/`: ongoing responsibilities without a fixed end date (`area-template.md`).
- `projects/`: bounded outcomes with milestones, tasks, risks, and decisions (`project-template.md`).
- `knowledge/`: durable notes, references, and research.
- `knowledge/claims/`: reusable personal claim records with structured evidence,
  provenance, temporal metadata, and status
  (`knowledge/claims/claim-template.md`).
- `ideas/`: possible future work and observations (`idea-template.md`).
- `decisions/`: questions, options, evidence, trade-offs, and outcomes (`decision-template.md`).
- `monitors/`: things to watch for change over time (`monitor-template.md`).
- `tasks/`: concrete actions that can be completed (`task-template.md`).
- `calendar/`: planning notes, meeting agendas, and event context (`event-note-template.md`).
- `people/`: relationship context and person records (`person-template.md`).
- `shopping/`: product research and purchase candidates (`item-template.md`).
- `travel/`: trips, itineraries, and travel research (`trip-template.md`).
- `finance/`: budgets, spending notes, and financial reviews (`finance-template.md`).
- `finance/intake/`: source batches for statements, receipts, payslips, and manual entries.
- `finance/accounts/`: non-secret account-to-ledger mappings and reconciliation configuration.
- `finance/portfolios/`: holdings scope, dated valuations, prices, cost basis, and allocation notes.
- `finance/reviews/`: periodic cash-flow, spending, net-worth, and portfolio reviews.
- `health/`: family medical-history records separated into profiles, history,
  conditions, treatments, and source-linked reviews.
- `archive/`: completed or inactive material retained for reference.
- `sources/`: retained originals, source records, immutable extraction artifacts,
  and evidence manifests created by durable ingestion.
- `inbox/ingestion/`: durable ingestion intake records that survive runtime queue
  cleanup.
- `inbox/daily-briefing/`: dated briefing reports generated by the briefing
  workflow (`YYYY-MM-DD.md`).

The default workspace does not include domain-specific subfolders such as
`travel/ideas/` or `learning/topics/`. Start with the core domains and add an
extension only when a recurring need justifies it. For example, an early travel
possibility can live in `ideas/` with travel context; a committed itinerary can
use `travel/`. A learning practice can use an `areas/` record linked to goals,
projects, tasks, and knowledge. The finance subdomains listed above are a
deliberate registered extension because transaction intake, account mappings,
portfolio valuation, and periodic review have different lifecycles. Health is a
registered extension because identity boundaries and clinical record types need
stronger structure than a general area or knowledge note. Other dedicated
extensions remain optional, not automatic.

## Starter template format

Starter files use YAML frontmatter for structured record metadata. Every
frontmatter template declares its JSON Schema in `$schema`, as a local relative
path from that template (for example, `goals/goal-template.md` can use
`$schema: ./goal-template.schema.json`). The referenced schema must remain
inside the workspace root. That schema applies to every non-template Markdown
file in the template directory and its subdirectories. A more-specific nested
template governs its own subtree.

In ordinary starters, a `null` value is an unfilled field to complete when
creating a record; inline comments show allowed values or expected formats.
The `$schema` property is a validator directive and is not record metadata.
Replace the `<...>` text in ordinary template title headings. Users may
customize their workspace copy by editing the template and its referenced
schema together; profile sync preserves those edits. Validate on demand with the
protected `workspace-template-customization` system skill, or run this in
Hermes:

```sh
/opt/hermes/.venv/bin/python /opt/data/skills/workspace-template-customization/scripts/validate_workspace.py \
  --workspace-root /opt/data/workspace \
  --skill-templates-root /opt/data/skills
```

Claim records use the same template-referenced schema workflow as other
workspace domains. Their schema validates frontmatter; the template documents
the Markdown body structure and evidence practices. Quote ISO-8601 dates;
timestamps must include a timezone offset.

The delegation policy is YAML rather than a Markdown record. Its local schema
defines the available authority settings, and the workspace validator checks it
alongside the registry and record templates. Treat policy changes as user-owned
configuration and review them before enabling broader authority.

Financial intake and review records organize the bookkeeping workflow; the
hledger journal remains the transaction source of truth. Retained statements,
payslips, and exports captured by ingestion live under `sources/`; intake
records may contain stable references and extracted facts, but never
credentials, account numbers, or raw authentication data. Document-unlock
passwords belong only in the dedicated plaintext password-profile file.

## Delegated Actions

The assistant may act when either the current request explicitly authorizes the
scoped action or `assistant-policy.yaml` grants standing delegation. Routine
workspace actions may run without a new approval when the policy is enabled and
the destination is registered. Ambiguous interpretations remain pending.

Directly reported personal facts may be recorded with source and provenance
when `delegation.memory.direct_reports` is `record`. Observations and inferences
must follow their configured memory mode; the default keeps them as candidates.
Sending messages, changing external calendars, purchases, financial
transactions, permanent deletion, and destructive overwrites are not authorized
by the default workspace delegation.

The local `record_financial_data` action may authorize clear journal postings
and reconciliation metadata when `finance/` is an allowed domain. It never
authorizes an external transfer, purchase, trade, or account change; those use
the separate `financial_transactions` external setting.

For every delegated write, preserve the source where available, avoid silent
overwrites, report the meaningful change, and record the authority used in the
review or output. Scheduled work uses the same policy and must not exceed its
`scheduled_work.allowed_actions`.

## Working rules

Capture first in `inbox/` when the final category is unclear. Link actions to a
project or goal when that context is known. Prefer small Markdown files with
clear dates and titles over opaque databases. Use `knowledge/claims/` for
reusable personal statements in Markdown files with YAML front matter, and
distinguish direct reports from observations and inferences. Move inactive
material to `archive/` and retain it during routine reviews.

Use registered semantic paths for automatic routing. Ordinary nested folders
inside an authorized domain do not need registration; a scoped file request
includes its necessary parent directories. Use `inbox/` when classification is
genuinely unclear. A registered path alone does not authorize a write; check
`assistant-policy.yaml` as well.

## Workspace Growth

The assistant is the workspace architect; the user approves the design rather
than editing infrastructure. When a recurring use case needs reusable structure:

1. Inspect existing organization and recommend the smallest suitable location.
2. Draft the folders, template, and necessary registry/routing changes. Prefer a
   plain Markdown template; add a schema only when validation, querying, or
   automation brings real value. Do not register every ordinary folder.
3. Explain the proposed outcome, format, placement, and effects on existing
   content. Offer **Confirm, Adjust, or Cancel**; keep exact file changes
   reviewable. Include the user's original requested output in the proposal.
4. Apply only the confirmed batch, validate it, and continue the original task
   automatically. Approval does not authorize other restructuring, policy
   changes, destructive actions, or external effects. Revise and reapprove if
   the scope changes; do not rewrite existing records as an incidental migration.

For example, propose `projects/daily-menu/` with a reusable menu template and
the requested dated menu together. One confirmation creates the useful
structure **and** the menu, not just scaffolding. A schema is not required.

Registered extensions are user-owned and survive profile updates. The protected
`workspace-template-customization` system skill validates registry changes but
does not apply them without explicit approval.

Claims are the authoritative workspace memory. Hermes runtime memory may cache
claims for retrieval, but an unreferenced Hermes memory is not a durable fact.
Keep inferred claims as candidates until they have provenance and review.

This template contains no personal records. Keep credentials, tokens, private
exports, session logs, and service caches outside the tracked template.
